# Design

## Context

- Уровень сейчас запускает `LevelRunner` (`web/app/_components/LevelRunner.tsx`): берёт компонент уровня из модуля игры и получает результат через `onFinish`. Сверяются только `gameId` и `levelId`, остальной результат сохраняется как есть (`recordLevelResult` в `web/core/progress`).
- Реестр (`web/core/registry`) проверяет манифест и уже допускает модуль игры без `levelComponents`, но `LevelRunner` в этом случае показывает ошибку "нет компонента".
- Все данные пользователя лежат в LocalStorage на источнике портала. Любой скрипт с тем же источником может их прочитать и переписать.
- Статические файлы отдаются из `web/public`. Заголовки из `headers()` в `next.config.ts` применяются и к ним (проверено по документации Next.js 16 в `node_modules/next/dist/docs`).
- Unity в окружении разработки нет, поэтому Unity-часть пишется по документации и проверяется командой игры.

## Goals / Non-Goals

**Goals:**
- Команда игры сдаёт папку сборки, манифест и тексты и не пишет ни строки для портала, кроме вызовов SDK.
- Код игры не может прочитать или подделать данные пользователя, даже если открыть сборку напрямую по адресу.
- Ошибка или зависание игры не ломают портал.
- Протокол можно развивать, не ломая уже сданные сборки.

**Non-Goals:**
- Загрузка сборок с внешнего домена или CDN (только `/game-builds/<gameId>/` в том же развёртывании).
- Полноэкранный режим, пауза, сохранение прогресса внутри уровня, передача игре имени игрока.
- Свой сервер раздачи сжатых сборок Unity (Brotli/gzip с `Content-Encoding`).
- Обновление требования к экрану библиотеки игр в `core-platform`.

## Decisions

### D1. Сборка в iframe, а не встраивание скриптов на страницу портала

Сборка открывается во фрейме по адресу `runtime.entry?level=<levelId>`.

- **Почему:** Unity и three.js сами управляют `canvas`, глобальными переменными и циклом отрисовки. Во фрейме у них свой документ, они не конфликтуют со стилями и React портала, а выгрузка уровня - это просто удаление фрейма.
- **Отклонено:** загрузка скрипта игры прямо на страницу уровня (нет изоляции, утечки памяти между уровнями); Module Federation и удалённые React-модули (требуют React от команды игры, Unity не подходит).

### D2. Изоляция: `sandbox="allow-scripts"` плюс заголовок CSP `sandbox` для `/game-builds/*`

У фрейма атрибут `sandbox="allow-scripts"` без `allow-same-origin`, поэтому у игры непрозрачный источник `null` и нет доступа к LocalStorage, cookie и `window.parent.document` портала. Дополнительно `next.config.ts` отдаёт для `/game-builds/:path*` заголовок `Content-Security-Policy: sandbox allow-scripts`. Без него сборку можно открыть напрямую по адресу, и тогда она выполнится на источнике портала с полным доступом к его данным.

- **Отклонено:** `allow-same-origin` (игра получила бы доступ к LocalStorage портала и могла бы выдать себе дипломы); отдельный поддомен для сборок (честная изоляция, но требует второго хоста и настройки развёртывания; можно перейти позже, протокол не изменится).

### D3. CORS для файлов сборки

Непрозрачный источник делает запросы к файлам сборки межисточниковыми: модули `<script type="module">`, `fetch` и XHR загрузчика Unity получают ответ, только если сервер разрешил это явно. `next.config.ts` добавляет для `/game-builds/:path*` заголовок `Access-Control-Allow-Origin: *`. Файлы сборок публичные и не содержат данных пользователя, поэтому открытый CORS безопасен.

### D4. Протокол сообщений

Все сообщения - объекты с полями `source` и `version`. Портал проверяет `event.source === iframe.contentWindow`: проверка `event.origin` бесполезна, у изолированного фрейма он всегда `"null"`. Портал отправляет сообщения с `targetOrigin: "*"` по той же причине; в них нет ничего секретного.

```
 игра -> портал  { source: "portal-game", version: 1, type: "ready" }
                 { source: "portal-game", version: 1, type: "level-result",
                   score, maxScore, completed }
                 { source: "portal-game", version: 1, type: "exit" }
                 { source: "portal-game", version: 1, type: "error", message }
 портал -> игра  { source: "portal", version: 1, type: "start", gameId, levelId }

 состояния уровня:
   loading --ready--> running --level-result--> finished (экран итога)
      |                  |------exit---------> abandoned (экран "не завершён")
      |                  |------error--------> failed (запасной экран)
      +--timeout/error-------------------------> failed
   кнопка выхода портала из любого состояния --> библиотека игр
```

Разбор и проверка сообщений - чистые функции в `web/core/bridge/` (тестируются без браузера). Компонент фрейма в `web/app/_components/IframeLevel.tsx` только держит состояние и подписку на `message`.

- **Почему `gameId` и `levelId` не берутся из сообщения:** их знает портал, игра не должна иметь возможности записать результат другому уровню.
- **Почему время считает портал:** часы игры могут остановиться при сворачивании вкладки или быть подделаны; портал считает от отправки `start` до получения результата.
- **Выход без результата не сохраняет попытку:** у портала нет `maxScore`, а попытка с `maxScore=0` не пройдёт проверку из D6. Игра, которая хочет сохранить брошенную попытку с очками, отправляет `level-result` с `completed: false`.

### D5. Объявление сборки в манифесте

Новое необязательное поле `runtime`:

```ts
runtime?: {
	kind: "iframe";
	entry: string;            // "/game-builds/<gameId>/index.html"
	readyTimeoutSec?: number; // по умолчанию 30
};
```

Проверка манифеста требует, чтобы `entry` начинался с `/game-builds/<gameId>/`, не содержал `..`, `//` и схемы. `LevelRunner` выбирает `IframeLevel`, если `runtime` задан, иначе компонент уровня. Модулю iframe-игры `levelComponents` не нужны.

- **Отклонено:** отдельный тип модуля для iframe-игр (пришлось бы менять реестр и все места, где он используется); общий React-компонент `IframeLevel`, который игра сама кладёт в `levelComponents` (лишний код у каждой команды, легко ошибиться с путём).

### D6. Проверка результата в ядре

Функция проверки `LevelResult` живёт рядом с проверкой манифеста в `web/core/contract/`, вызывается в `recordLevelResult` до записи. При отказе `LevelRunner` показывает сообщение "результат не удалось засчитать" (текст в `texts/common.ts`), а причина пишется в журнал через `debugLog`. Проверка общая для React- и iframe-игр.

### D7. Запасной экран

- React-игры: `LevelRunner` оборачивает компонент уровня в error boundary (классовый компонент, в React 19 по-прежнему единственный способ перехватить ошибку отрисовки). Повтор - смена `key`, которая заново монтирует уровень.
- iframe-игры: состояние `failed` при `error` или таймауте; повтор пересоздаёт фрейм.
- Оба случая рисуют один компонент запасного экрана с текстами из `texts/common.ts`.

### D8. SDK

```
 web/sdk/
 	web/portal-bridge.js            обычный скрипт, глобальный объект PortalBridge
 	unity/Plugins/PortalBridge.jslib
 	unity/Scripts/PortalBridge.cs
 	unity/WebGLTemplates/Portal/index.html
 	README.md                       как подключить, ссылки на docs/adding-game.md
```

- `portal-bridge.js` - обычный скрипт без сборщика и зависимостей, чтобы его можно было подключить и в three.js-проект, и в шаблон Unity. API: `PortalBridge.onStart(callback)`, `PortalBridge.finish({ score, maxScore, completed })`, `PortalBridge.exit()`, `PortalBridge.reportError(message)`. Сообщение `ready` отправляется при первом вызове `onStart`, чтобы игра не получила `start` раньше, чем готова его обработать.
- Unity: `.jslib` вызывает функции `PortalBridge` из скрипта, подключённого шаблоном; `PortalBridge.cs` даёт C#-методы `Finish`, `Exit`, `ReportError` и событие `OnStart(levelId)`, которое приходит через `SendMessage` на объект с заданным именем.
- Копия `portal-bridge.js` лежит в папке сборки примера. Тест сверяет её с `web/sdk/web/portal-bridge.js`, чтобы копии не разошлись.
- **Отклонено:** npm-пакет SDK (командам Unity npm не нужен, а публикация пакета - отдельная работа).

### D9. Пример на three.js из заглушки `city-builder`

Заглушка становится простой рабочей игрой: изометрическая сетка, игрок ставит дома, дороги и электростанции, цель уровня - набрать население при ограниченном бюджете. Цели и бюджет зависят от уровня. Результат: `score` - достигнутое население в пределах цели, `maxScore` - цель уровня.

- three.js кладётся в сборку как один файл ES-модуля `public/game-builds/city-builder/vendor/three.module.min.js` (лицензия MIT, файл лицензии рядом). Скачивание файла один раз при реализации требует разрешения пользователя.
- **Почему не npm-зависимость портала:** игра - отдельная сборка, портал не должен тянуть three.js в свой бандл; так же будут устроены настоящие игры команд.
- **Почему не CDN:** игра работала бы только с интернетом и зависела от чужого хоста.
- React-уровень `CityBuilderLevel` удаляется, `inDevelopment` снимается. Заглушка `pixel-lab` остаётся React-заглушкой.

### D10. Проверка тире и линтер для новых папок

`scripts/check-dashes.mjs` получает цели `sdk` и `public/game-builds` с исключением папок `vendor`. ESLint проверяет `web/sdk/web/*.js` как браузерный скрипт; `public/` и `vendor` в линтер не входят.

## Risks / Trade-offs

- [Unity в непрозрачном источнике не имеет IndexedDB: падает кэширование данных и `PlayerPrefs`] → в шаблоне Unity и документации требование выключить Data Caching и не полагаться на `PlayerPrefs`; прогресс уровня живёт только в памяти.
- [Сжатая сборка Unity (`.br`, `.gz`) не загрузится без `Content-Encoding`] → документация требует сборку с Decompression Fallback или без сжатия.
- [Next.js может отдавать `.wasm` не с типом `application/wasm`, тогда Unity переходит на медленную загрузку] → проверить тип при реализации; при необходимости добавить заголовок `Content-Type` для `*.wasm` в `headers()`.
- [Большие сборки Unity раздувают репозиторий] → рекомендовать Git LFS для `public/game-builds/**/Build/*`; настройку LFS делает пользователь.
- [Unity-SDK не проверен в этом окружении] → помечен в README как непроверенный до первой Unity-сборки; протокол покрыт тестами со стороны портала и веб-SDK.
- [Таймаут 30 секунд мал для тяжёлой Unity-игры на медленном интернете] → поле `readyTimeoutSec` в манифесте.
- [Игра может завалить портал сообщениями] → портал реагирует только на ожидаемый тип в текущем состоянии, остальное игнорирует без записи.

## Migration Plan

Миграции данных нет: формат попыток в LocalStorage не меняется. Новая проверка результата отбрасывает только заведомо неверные результаты; старые попытки в хранилище не перепроверяются. Откат - убрать `runtime` из манифеста примера и вернуть React-заглушку.

## Open Questions

- Нужен ли позже отдельный поддомен для сборок (сильнее изоляция, нужен второй хост). На протокол и SDK не влияет.
