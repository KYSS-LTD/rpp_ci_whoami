# Design

## Context

Портал поддерживает два способа подключения игры: React-модуль и готовая веб-сборка в изолированном фрейме (capability `game-iframe-bridge`, `web/docs/adding-game.md`, `web/docs/game-bridge-protocol.md`, `web/sdk/README.md`). Игра `cooking` подключается готовой веб-сборкой. Мотивация - в proposal.md, требования - в specs/.

Что это значит для игры:
- Фрейм открывается с `sandbox="allow-scripts"` без `allow-same-origin`: нет LocalStorage, cookie, IndexedDB, нет доступа к странице портала. Все файлы игры грузятся из `/game-builds/cooking/`, внешние CDN запрещены. Портал отдаёт сборку с `Access-Control-Allow-Origin: *`.
- Обмен идёт через `PortalBridge` (`web/sdk/web/portal-bridge.js`): `onStart` (первый вызов сообщает о готовности), `finish({ score, maxScore, completed })` один раз за запуск, `exit()` без результата, `reportError(message)`. Условия результата: `0 <= score <= maxScore`, `maxScore > 0`. `gameId`, `levelId` и `durationSec` портал берёт из запуска, время считается от старта по сообщению `ready`.
- Без портала сборка работает автономно: `/game-builds/cooking/index.html?level=easy` получает старт сразу.
- `web/games/cooking/` на стороне портала содержит только манифест с `runtime`, тексты витрины и модуль `{ manifest }`. Строка в `web/core/registry/index.ts`, строка `cook` в `web/texts/professions/index.ts` и кадры в `web/public/game-previews/cooking/` - остальные точки касания.
- Встроенная панель браузера Claude Code блокирует запросы изолированных фреймов: уровень в портале проверяется в обычном браузере, сама сборка - по прямому адресу.
- Стиль кода по `CodeStyle.md`: табы, комментарии на русском, тексты в отдельных файлах, режим отладки одной переменной в `.env`.
- Игровой интерфейс (HUD, подсказки, оверлеи, сенсорное управление) использует HTML и CSS внутри фрейма. Разработчики сверяются с руководством `modern-web-guidance`.

Раскладка файлов:

```
web/
  games/cooking/              портал: manifest.ts, texts/index.ts, index.ts
  games/cooking/           исходники игры
    index.html  vite.config.ts  package-скрипты в web/package.json
    public/                   portal-bridge.js (копия sdk/web), models/ (glTF и атлас), tutorial/ (GIF подсказок)
    src/
      main.ts                 запуск: загрузка, onStart, цикл
      contracts.ts            общие типы (состояние, ввод, события, снимок для HUD)
      sim/ input/ render/ hud/ config/
      texts/                  тексты игры: по файлу на область (hud, controls...), общий index.ts
  public/game-builds/cooking/ результат сборки (хранится в git, как city-builder)
  public/game-previews/cooking/ кадры для библиотеки игр
```

## Goals / Non-Goals

**Goals:**
- Вся игровая логика (рецепты, клиенты, терпение, официант, путь, счёт) работает без браузера и three.js и проверяется тестами vitest.
- Один источник данных об уровне: из него строятся расстановка мебели, коллизии, навигационная сетка, точки взаимодействия и слоты очереди.
- Каждый из трёх уровней доказуемо проходим: проверка выполнимости ботом входит в тесты.
- Сборка работает и внутри портала, и по прямому адресу.

**Non-Goals:**
- Физический движок, скелетная анимация, звук.
- Универсальный движок игр: код игры живёт в `games/cooking` и не выносится в ядро портала.
- React, Next.js и R3F внутри игры.
- Серверная проверка результатов.

## Decisions

### D1. Сборка: Vite, TypeScript и three.js

Игра - отдельный проект в `web/games/cooking/`, собирается Vite в `web/public/game-builds/cooking/`. Зависимости `vite`, `three`, `@types/three` - devDependencies `web/package.json`, скрипты `dev:cooking` и `build:cooking`. Настройки сборки:
- `base: "./"`, чтобы пути работали из `/game-builds/cooking/`;
- three.js выделяется в чанк внутри папки `vendor/`: так его пропускают `check:dashes` и ESLint (в проекте это уже принято для сторонних библиотек);
- `envDir` указывает на `web/`, `envPrefix` содержит `NEXT_PUBLIC_`, чтобы переменная отладки `NEXT_PUBLIC_DEBUG` была одной для портала и игры.
- Альтернатива: R3F внутри Next. Отвергнуто: игра живёт во фрейме, а не в страницах Next, и теряется изоляция.
- Альтернатива: библиотека three.js положена в `vendor/` вручную без сборщика, как у `city-builder`. Отвергнуто: игра на тысячи строк TypeScript с тестами требует сборщика и типов.
- Альтернатива: Babylon.js, PlayCanvas. Отвергнуто: тяжелее и не нужны.

### D2. Симуляция отдельно от рендера

```
ввод -> sim.step(dt) -> состояние -+-> render (three.js, чтение)
                                   +-> HUD (DOM, подписка)
```

- `sim/` не импортирует three и DOM. Шаг фиксированный (60 Гц, накопитель времени), время смены - время симуляции, а не часов. Скрытая вкладка ставит игру на паузу.
- HUD - обычный DOM-слой над canvas. Он читает снимок состояния через простое хранилище с подпиской и обновляется не чаще 10 раз в секунду. Библиотеки интерфейса нет.
- Альтернатива: Preact или React во фрейме. Отвергнуто: лишняя зависимость ради десятка элементов.
- Случайность идёт из seeded-генератора (mulberry32). Весь день воспроизводим по seed.
- Общие типы лежат в `src/contracts.ts` и согласуются до начала параллельной работы.

### D3. Уровень как данные

Конфигурация уровня описывает прямоугольники мебели и станций на сетке 0.5, точки столов и стульев, окно выдачи, дверь, слоты очереди, параметры (таймер, меню, число столов, официантов, терпение). Из неё же строятся навигационная сетка и коллизии. Меши мебели расставляются по тем же данным.
- Альтернатива: брать навигацию из загруженных мешей. Отвергнуто: тесты и бот не должны зависеть от glTF.
- Три уровня используют один набор моделей, отличаются раскладкой и параметрами.

### D4. Ввод: один нормализованный интерфейс

Слой ввода собирает клавиатуру (по `event.code`, чтобы русская раскладка не ломала WASD, E и Q), мышь (`pointer`-события, `contextmenu` отключается) и касания (по `pointerId`, `touch-action: none`) в структуру `{ moveVector, actionPressed, workHeld }`. Симуляция не знает об устройстве. При потере фокуса ввод сбрасывается. Режим касаний включается по `(pointer: coarse)` и первому касанию.
- Взгляд хранится как индекс 0..7 и выбирается по `moveVector` с гистерезисом на границах секторов. Плавный поворот рисует рендер, симуляция использует индекс сразу.

### D5. Движение игрока и выбор цели

Игрок - круг, столкновение с прямоугольниками мебели со скольжением вдоль стены. Цель взаимодействия - ближайший объект к точке перед игроком по направлению взгляда (около 0.9 вперёд), с допуском. Цель подсвечивается.
- Альтернатива: физический движок (rapier, cannon). Отвергнуто: геометрия сеточная, лишняя зависимость и вес.

### D6. Предметы и рецепты - данные

Предмет описывается видом и состоянием (`steak/raw`, `patty/cooked`, ...). Станции и рецепты - таблицы переходов (`резка`: состояние A -> B за N секунд удержания; `готовка`: A -> B -> сгоревшее по таймерам). Составное блюдо это сборка: мультимножество ингредиентов, которое может лежать в руке, на поверхности или на тарелке (модель предметов версии 2: D17). Как только содержимое сборки совпадает с рецептом блюда, сборка получает признак блюда (меш `food_*` рисуется для блюда на тарелке).
- Сковороды закреплены на плитах и не переносятся. Кастрюля для рагу переносимая (D21).
- Промежуточные слои бургера рисуются стопкой мешей (`bun_bottom`, `burger_cooked`, `*_slice`, `bun_top`) до превращения в готовое блюдо.

### D7. Расписание дня и «бюджет работы»

Весь день (время прихода, размер группы, блюда) строится в начале уровня из seed. Каждое блюдо несёт трудоёмкость, а суммарная нагрузка в скользящем окне ограничена долей (начально 70%) пропускной способности эталонного бота. Приходы ограничены окном от 0 до T-60 секунд.
- Альтернатива: пуассоновский поток без ограничений. Отвергнуто: возможны всплески, которые невозможно обслужить, а при нулевой терпимости это нечестный проигрыш.
- Расписание задаёт знаменатель для HUD («обслужено X из N») и `maxScore`.
- При запуске уровня seed выбирается случайно из списка проверенных (каждый seed заранее прогнан ботом, см. D11). Так разнообразие остаётся, а невыполнимого расписания не бывает.

### D8. Терпение двух фаз

Фаза A (очередь): фиксированное время на уровень. Фаза B (за столом): `базовое + k * трудоёмкость блюда + запас на путь официанта`. У каждого клиента свой таймер, истечение у любого члена группы - провал смены. Остаток терпения при подаче определяет чаевые (`score`). Значения и коэффициенты - в конфиге уровня и калибруются ботом.

### D9. Навигация: A* по сетке

Сетка 0.5, восемь соседей без срезания углов, эвристика octile, затем сглаживание по линии видимости. Препятствия: мебель, раздутая на радиус агента, стулья чужих мест. Агенты NPC сталкиваются только со статикой, между собой и с игроком расталкиваются мягко (силой разделения), а не блокируют друг друга. Если путь не продвигается дольше порога, он перестраивается.
- Альтернативы: навигационный меш (избыточно для сеточной раскладки), RVO/ORCA (избыточно для 2-6 агентов), поле потоков на каждую цель (целей много, A* дешевле).
- Один модуль пути используют официанты и клиенты.

### D10. Назначение заказов официанту

Блюдо в окне привязывается к самому старому открытому заказу того же вида (FIFO по времени появления заказа). Свободный официант с минимальной длиной пути до окна берёт тарелку. Вместимость: 1 тарелка (easy, medium), до 2 на hard, при двух тарелках на один стол они идут одним рейсом.
- Альтернатива: игрок выбирает стол при сдаче. Отвергнуто: усложняет управление и противоречит идее «официант принимает решение».

### D11. Проверка выполнимости эталонным ботом

Бот в vitest проходит уровень в симуляции (жадный планировщик, идеальное движение по A*, без ошибок) и даёт нижнюю оценку времени. Тесты требуют: все клиенты дня обслужены до T, терпение не истекает, очередь не превышает число слотов, последние 60 секунд достаточны для обслуживания очереди. Выполняется для набора seed на каждый из трёх уровней.
- Альтернатива: ручное тестирование. Отвергнуто: не воспроизводимо при изменении параметров.

### D12. Завершение смены через мост

Фазы симуляции: `ready` -> `running` -> `failed` или `finished`.
- Успешный конец (все обслужены, в том числе досрочно) или таймер без обслуженных клиентов: `PortalBridge.finish({ score, maxScore, completed })`.
- Провал (уход клиента): симуляция замирает, игра показывает оверлей с причиной, после кнопки «Продолжить» вызывает `finish` с `completed=false` и набранным `score`.
- Выход игрока из меню паузы: `PortalBridge.exit()`, результат не сохраняется (экран «Уровень не завершен» рисует портал).
- Фатальная ошибка (нет WebGL, не загрузились модели): `PortalBridge.reportError(...)`, портал показывает экран с повтором.
- После отправки результата или выхода игра останавливает цикл и не отправляет ничего повторно.

### D13. Готовность и загрузка

Сначала загружаются все нужные модели, затем вызывается `PortalBridge.onStart`: первый вызов сообщает порталу о готовности. Пока идёт загрузка, портал показывает собственный индикатор. `runtime.readyTimeoutSec` - 60 секунд (по умолчанию 30 мало для около 50 моделей на медленном канале). Уровень берётся из сообщения старта, а не из адреса. `durationSec` считает портал от старта, поэтому стартовый экран с подсказками входит в него: он короткий и без времени ожидания.

### D14. Ассеты и персонажи

Нужные модели (около 50) и атлас копируются в `web/games/cooking/public/models/`, Vite кладёт их в `public/game-builds/cooking/models/`. Все пути относительные, `GLTFLoader` и текстуры грузятся из той же папки: изолированный фрейм разрешён благодаря CORS-заголовку портала. Персонажи (повар, официант, клиенты) строятся из примитивов в цветах атласа, покачивание при ходьбе по синусу. Иконки блюд для HUD рендерятся один раз из glTF во внеэкранный canvas, запасной вариант - текстовая подпись.
- Альтернатива: сторонний пак персонажей с анимациями. Отложено: не меняет контракты, лицензию надо проверить отдельно.
- Альтернатива: FBX или OBJ. Отвергнуто: glTF стандарт веба, нужен один формат.

### D15. Камера и раскладка

Камера без поворота, наклон около 50°, перспектива, весь ресторан в кадре. Передняя стена заменена на `wall_half`. Кухня и зал разделены стеной с окном выдачи, дверь с улицей и слоты очереди находятся в зоне видимости камеры. Оси камеры совпадают с осями сетки: W всегда означает «вверх» на экране. Размер canvas следует за размером фрейма (на телефоне и на ПК он разный).

### D16. Отладка и мост-копия

`NEXT_PUBLIC_DEBUG=true` включает отладочный оверлей (сетка навигации, пути, зоны). Значение подставляется при сборке (`dev:cooking` читает его на лету). Копия `portal-bridge.js` берётся из `sdk/web/` шагом перед сборкой, а её путь добавляется в `bridgeCopies` теста `sdk/sdk-consistency.test.ts`, чтобы копия не отставала.

### D17. Модель предметов версии 2: сборка без тарелки, тарелка как последний этап

Предмет это `IngredientItem` (один ингредиент), `AssemblyItem` (сборка) или `PotItem` (кастрюля, D21). `AssemblyItem` хранит `contents` (мультимножество ингредиентов), `dish` (блюдо, если содержимое совпало с рецептом меню, иначе пусто) и флаг `plated` (лежит на тарелке). Пустая тарелка это сборка с `plated = true` и пустым `contents`. Одиночный ингредиент остаётся `IngredientItem`: сборка появляется, когда соединяются два предмета или предмет кладут на тарелку.
- Принятие: ингредиент соединяется со сборкой, только если `contents` вместе с ним входят в мультимножество хотя бы одного рецепта меню уровня (как раньше для тарелки); сгоревшее не соединяется ни с чем и годится только для урны.
- Блюдо без тарелки (`dish` задан, `plated = false`) можно носить, ставить на прилавок и класть на тарелку, но окно выдачи его не принимает: окно принимает только `plated = true` и `dish` не пусто (отказ `dishNotPlated` для блюда без тарелки, `dishNotReady` для недоделанного).
- Альтернативы. Отдельный тип "сборка" рядом с прежним `PlateItem`: две почти одинаковые структуры и дублирование правил соединения, отвергнуто. Автосборка по рецепту без промежуточного состояния: теряется свобода порядка и невозможно показать полуготовую сборку, отвергнуто. Тарелка как неподвижная станция: по сценарию игрок несёт тарелку в руках, отвергнуто.

### D18. Соединение предметов: где остаётся результат

Игрок нажимает "взять/положить" (E) на станции, держа предмет. Результат определяет такой порядок:
- ящик: предмет из ящика соединяется с предметом в руке (пример: жареная котлета в руке, E на ящике с булочками, в руке бургер без тарелки); без возможного соединения рука занята, отказ `handBusy`;
- плита или духовка с готовым: готовое соединяется с предметом в руке (в том числе с тарелкой), результат остаётся в руке;
- прилавок или доска с предметом, в руке предмет: если один из двух на тарелке, носителем результата становится тот, что на тарелке (в руке остаётся в руке, на поверхности остаётся на поверхности); если ни один не на тарелке, результат остаётся на поверхности; две тарелки не соединяются;
- стойка тарелок: предмет или сборка в руке, которые можно положить на тарелку, оказываются на новой тарелке в руке; пустую тарелку стойка принимает обратно, как раньше.
Правило "что на тарелке, то остаётся у носителя" сохраняет прежнее поведение (тарелка в руке забирает ингредиент с прилавка, ингредиент в руке ложится на тарелку на прилавке) и делает результат предсказуемым.

### D19. Резка на любой поверхности, бонус доски

Сырой нарезаемый предмет принимают прилавок и разделочная доска. Рабочее действие режет за `cutSec` на прилавке и за `cutSec * boardCutDurationFactor` (0.8) на доске; прогресс привязан к предмету на поверхности и сохраняется при отпускании. Нарезанный предмет берётся в руку или соединяется (D18). Остальные правила резки не меняются.

### D20. Скорость готовки и две полосы прогресса

Параметр `cookDurationFactor` (0.8) умножает `cookSec` каждого процесса готовки (сковорода, духовка, кастрюля); `burnSec` не меняется. Над станцией рисуются две полосы: зелёная заполняется за время готовки (`progress` 0..1), после готовности заполняется красная до подгорания (`burnProgress` 0..1, растёт; прежняя убывающая полоса убирается). У станции без подгорания (кастрюля) красной полосы нет.

### D21. Кастрюля: переносимый предмет, кран, плита без подгорания

- `PotItem`: `hasWater`, нарезанные овощи `contents`, `cookProgressSec` (прогресс варки сохраняется в предмете), `portions` (порции готового рагу). Кастрюля стоит на столе (`counter` с `startItem = "pot"`) в начале смены на любой сложности и остаётся в игре весь раунд: урна её не принимает.
- Кран (`tap`, на всех сложностях рядом с плитами): кастрюля в руке, E на кране наливает воду (`hasWater = true`). Раковины и мойки нет.
- Конфорка (`stove`): принимает кастрюлю (E с кастрюлей в руке на пустой конфорке) и возвращает её в пустую руку. Овощи кладутся в кастрюлю, когда в ней есть вода (иначе отказ `needsWater`): ингредиент в руке, E на кастрюле, стоящей на конфорке или на прилавке ("смешать на столе"), либо кастрюля в руке, E на прилавке с овощем.
- Набор полный (вода и по одному нарезанному carrot, potato, onion) и кастрюля стоит на конфорке: конфорка включается сама (`cookingStarted`). Пока набор неполный, конфорка выключена. Через `cookSec * cookDurationFactor` конфорка выключается (`cookingDone`), в кастрюле `stewPortionsPerBatch` порций. Подгорания у кастрюли нет. Если снять кастрюлю во время варки, прогресс остаётся в предмете и продолжится на конфорке.
- Порцию берёт тарелка: тарелка в руке, E на конфорке или прилавке с готовой кастрюлей (порция соединяется с тарелкой, уменьшая `portions`). Опустевшая кастрюля остаётся пустой и без воды.
- Станции `pan` (плита со сковородой) и `oven` не меняются. Вид станции `pot` из версии 1 удалён: вместо него `stove`.

### D22. Раскладка уровней: размеры, проходы, расположение станций

- При конфликте требований приоритет у соотношения площади кухни и зала 3:2. Внутренние полы имеют ширину 7.5 и 5 соответственно; глубина easy 6, medium 8, hard 10. Фактические площади кухня/зал: easy 45/30, medium 60/40, hard 75/50. Поэтому исходную цель уменьшить кухню до 0.6 прежней площади считать вторичной; сохраняются все станции и число столов (3, 4, 6), столы стоят плотными рядами.
- Проходы: магистраль от двери к столам и окну выдачи в зале не уже 1.5, между соседними столами не уже 1.0; подходы к местам доступны NPC. В кухне, где ходит только повар, проходы не уже 1.0.
- Тарелки (`plateStack`) стоят вплотную к окну выдачи, урна (`trash`) рядом с плитами (`pan`, `stove`) и духовкой. На всех сложностях есть стол с кастрюлей, кран рядом с конфоркой и конфорка для пятого дня кампании. Раковины нет.
- Раскладка проверяется прежними тестами достижимости и ботом.

### D23. Прогресс игры через мост

Блок данных игры (прогресс) это JSON-объект до 4096 байт (длина `JSON.stringify` в UTF-8). Портал хранит его в LocalStorage по `gameId` (единый модуль хранения), отдаёт в сообщении старта в поле `progress` (объект или `null`, когда блока нет или LocalStorage недоступен) и принимает обновления новым сообщением игры `progress` с полем `data`.
- Версия протокола остаётся 1: новое поле старта и новый тип сообщения не ломают старые игры (поле игнорируется) и старые порталы (неизвестный тип сообщения игнорируется по требованию версионирования).
- Обновление принимается только от фрейма запущенного уровня и только после старта, блок заменяется целиком (последнее значение), слишком большой, не объект или несериализуемый блок отбрасывается без ошибки для игры. Блок не содержит секретов и не влияет на результат уровня.
- Кнопка "Сбросить результаты" удаляет блоки данных всех игр вместе с остальными результатами.
- SDK: веб-SDK отдаёт блок как `start.progress` и даёт `saveProgress(data)` (проверяет размер и сериализуемость до отправки, возвращает `false` при отказе, в автономном режиме пишет в консоль); SDK Unity даёт `GetProgressJson()` и `SaveProgressJson(json)`.
- Блок cooking: `{ version: 1, cookedDishes: DishId[] }` (список блюд, которые игрок уже готовил). Неизвестная версия или битый блок читаются как пустой.
- Альтернатива: хранить прогресс в LocalStorage самой игры. Отвергнуто: изолированный фрейм без `allow-same-origin` не имеет доступа к хранилищу (D1 и риски первого этапа).

### D24. Подсказки перед началом смены и анимации

- "Блюдо приготовлено игроком": окно выдачи приняло блюдо (событие `dishAccepted`) при управлении игрока (эталонный бот прогресс не пишет, тесты проверяют это отдельно). Блюдо считается приготовленным на любом уровне: прогресс общий для игры.
- В фазе `ready` HUD перед кнопкой "Начать" показывает по одному окну (`dialog`) на каждое блюдо меню уровня, которого нет в `cookedDishes`: название блюда и анимации этапов с короткой подписью, кнопки "Дальше" и "Пропустить подсказки". Если все блюда меню приготовлены, окон нет. Сам показ подсказки прогресс не меняет.
- Этапы: бургер 4 (мясо и нарезка, жарка, булочка и котлета в руках, тарелка и окно), окорок 4 (ветчина в духовку, готовка и ожидание, забор из духовки, тарелка и окно), овощной бургер 4 (овощи и нарезка, жарка, булочка и котлета в руках, тарелка и окно), рагу 6 (кастрюля со стола и кран, нарезка овощей, овощи в кастрюлю, конфорка и варка, порция на тарелку, окно).
- Формат: GIF, 480x300 (16:10), 10 кадров в секунду, до 4 секунд, не более 128 цветов, не более 250 КБ на файл и около 5 МБ всего, файлы `web/game-src/cooking/public/tutorial/<блюдо>-<номер>.gif` (18 штук) и статичный первый кадр `<блюдо>-<номер>.png` для `prefers-reduced-motion`. Если картинка не загрузилась, остаётся подпись этапа.
- Как получать: скрипт `web/scripts/capture-tutorial.mjs` запускает dev-страницу игры в headless Chrome по CDP (как кадры превью), прокручивает настоящую симуляцию детерминированно (шаги симуляции без реального времени) по сценарию идеального игрока из `bot/tutorialScript.ts`, снимает кадры 10 раз в секунду и кодирует GIF библиотекой `gifenc` (devDependency). Анимации пересоздаются при смене внешнего вида игры. Альтернатива: записывать экран вручную. Отвергнуто: не воспроизводимо.

### D25. NPC не проходят сквозь стены

Требование проверяется инвариантом: ни один путь, выданный поиском пути, и ни один шаг NPC (клиентов и официантов) не пересекает блокирующий прямоугольник уровня; отдельный тест на путь с улицы к двери на трёх уровнях. Причину (раскраска сетки, сглаживание по линии видимости, проход у проёма двери, перенос в точку посадки) ищет владелец навигации; если причина в данных уровней (проём, `blocking` кусков стен), правит данные архитектор.

## Начальные значения баланса

Значения лежат в конфиге и калибруются ботом, на спецификации они не влияют.

| Операция | Значение |
|---|---|
| Резка (удержание) на прилавке | 2 с |
| Резка на разделочной доске | 2 с x 0.8 = 1.6 с |
| Котлета на сковороде | готова за 6 с x 0.8 = 4.8 с, сгорает ещё через 6 с |
| Окорок в духовке | готов за 8 с x 0.8 = 6.4 с, сгорает через 8 с |
| Рагу в кастрюле | готово за 10 с x 0.8 = 8 с, не пригорает |
| Время еды клиентом | 12 с |
| Бюджет работы | 70% пропускной способности бота |

## Risks / Trade-offs

- **[Загрузка glTF, `.bin` и текстур из изолированного фрейма]** -> первая задача проверяет это в портале в обычном браузере, пути относительные, при проблемах - упаковка моделей в один файл.
- **[Встроенная панель браузера блокирует iframe]** -> ручная проверка сборки по прямому адресу, потока портала - в обычном Chrome.
- **[`durationSec` считает портал, он включает стартовый экран и паузу]** -> принято, стартовый экран короткий. Время смены внутри игры считается по времени симуляции.
- **[Нулевая терпимость делает игру суровой]** -> щедрое терпение на easy, расписание с бюджетом работы, проверка бота.
- **[NPC застревают и проигрыш не по вине игрока]** -> мягкое расталкивание, перепланирование пути, тест на отсутствие дедлоков в симуляции.
- **[Производительность на слабых телефонах]** -> ограничение pixel ratio, один атлас, статичный декор через инстансинг, без тяжёлых теней.
- **[Нет персонажей в паке]** -> примитивы в стиле пака, смена на другой пак не затрагивает логику.
- **[Лицензия пака]** -> подтвердить перед публикацией, файл лицензии положить рядом с ассетами.
- **[Ввод: ПКМ, стрелки, потеря фокуса]** -> `contextmenu` и скролл блокируются внутри фрейма, сброс ввода на `blur`.
- **[Сборка и модели лежат в git]** -> как у `city-builder`; размер модели ограничен выбором около 50 файлов. Коммитит пользователь.
- **[Общие файлы проекта]** -> правки `scripts/check-dashes.mjs`, `sdk/sdk-consistency.test.ts`, `package.json` отмечены в задачах.
- **[Расширение моста затрагивает общий код портала]** -> версия протокола 1, поле и сообщение необязательные, тесты совместимости (старая игра с новым порталом и новая игра со старым), правки точечные и отмечены в задачах, SDK Unity обновляется вместе с веб-SDK.
- **[Соотношение кухни и зала 3 к 2 при плотных столах и проходе NPC не уже 1.5]** -> при конфликте с целью уменьшения кухни приоритет у соотношения; фактические площади в отчёте, проверка достижимости.
- **[Сборка без тарелки усложняет правила соединения]** -> единая модель `AssemblyItem`, одна матрица правил (D18), тесты по каждой паре станция и предмет, бот проходит все блюда.
- **[GIF-подсказки весят много и устаревают]** -> не более 250 КБ на файл, воспроизводимая съёмка скриптом, подпись этапа как запасной вариант.
- **[Общие файлы проекта]** -> правки `scripts/check-dashes.mjs` (папка `games/cooking`), `sdk/sdk-consistency.test.ts`, `package.json` минимальны и отмечены в задачах.
