# Design

## Context

Портал поддерживает два способа подключения игры: React-модуль и готовая веб-сборка в изолированном фрейме (capability `game-iframe-bridge`, `web/docs/adding-game.md`, `web/docs/game-bridge-protocol.md`, `web/sdk/README.md`). Игра `cooking` подключается готовой веб-сборкой. Мотивация - в proposal.md, требования - в specs/.

Что это значит для игры:
- Фрейм открывается с `sandbox="allow-scripts"` без `allow-same-origin`: нет LocalStorage, cookie, IndexedDB, нет доступа к странице портала. Все файлы игры грузятся из `/game-builds/cooking/`, внешние CDN запрещены. Портал отдаёт сборку с `Access-Control-Allow-Origin: *`.
- Обмен идёт через `PortalBridge` (`web/sdk/web/portal-bridge.js`): `onStart` (первый вызов сообщает о готовности), `finish({ score, maxScore, completed })` один раз за запуск, `exit()` без результата, `reportError(message)`. Условия результата: `0 <= score <= maxScore`, `maxScore > 0`. `gameId`, `levelId` и `durationSec` портал берёт из запуска, время считается от старта по сообщению `ready`.
- Без портала сборка работает автономно: `/game-builds/cooking/index.html?level=easy` получает старт сразу.
- `web/games/cooking/` на стороне портала содержит только манифест с `runtime`, тексты витрины и модуль `{ manifest }`. Строка в `web/core/registry/index.ts`, строка `cook` в `web/texts/professions/index.ts` и кадры в `web/public/game-previews/cooking/` - остальные точки касания.
- Встроенная панель браузера Claude Code блокирует запросы изолированных фреймов: уровень в портале проверяется в обычном браузере, сама сборка - по прямому адресу.
- Стиль кода по `CodeStyle.md`: табы, комментарии на русском, тексты в отдельных файлах, режим отладки одной переменной в `.env`.
- Игровой UI (HUD, подсказки, оверлеи, сенсорное управление) - обычный HTML и CSS внутри фрейма. Для него разработчики сверяются с руководством `modern-web-guidance` (`coocking/modern-web-guidance/skills/modern-web-guidance/SKILL.md`).

Раскладка файлов:

```
web/
  games/cooking/              портал: manifest.ts, texts/index.ts, index.ts
  game-src/cooking/           исходники игры
    index.html  vite.config.ts  package-скрипты в web/package.json
    public/                   portal-bridge.js (копия sdk/web), models/ (glTF и атлас)
    src/
      main.ts                 запуск: загрузка, onStart, цикл
      contracts.ts            общие типы (состояние, ввод, события, снимок для HUD)
      sim/ input/ render/ hud/ config/
      texts/                  тексты игры: по файлу на область (hud, controls...), общий index.ts
  public/game-builds/cooking/ результат сборки (хранится в git, как city-builder)
  public/game-previews/cooking/ кадры для библиотеки игр
```

## Goals / Non-Goals

**Goals:**
- Вся игровая логика (рецепты, клиенты, терпение, официант, путь, счёт) работает без браузера и three.js и проверяется тестами vitest.
- Один источник данных об уровне: из него строятся расстановка мебели, коллизии, навигационная сетка, точки взаимодействия и слоты очереди.
- Каждый из трёх уровней доказуемо проходим: проверка выполнимости ботом входит в тесты.
- Сборка работает и внутри портала, и по прямому адресу.

**Non-Goals:**
- Физический движок, скелетная анимация, звук.
- Универсальный движок игр: код игры живёт в `game-src/cooking` и не выносится в ядро портала.
- React, Next.js и R3F внутри игры.
- Серверная проверка результатов.

## Decisions

### D1. Сборка: Vite, TypeScript и three.js

Игра - отдельный проект в `web/game-src/cooking/`, собирается Vite в `web/public/game-builds/cooking/`. Зависимости `vite`, `three`, `@types/three` - devDependencies `web/package.json`, скрипты `dev:cooking` и `build:cooking`. Настройки сборки:
- `base: "./"`, чтобы пути работали из `/game-builds/cooking/`;
- three.js выделяется в чанк внутри папки `vendor/`: так его пропускают `check:dashes` и ESLint (в проекте это уже принято для сторонних библиотек);
- `envDir` указывает на `web/`, `envPrefix` содержит `NEXT_PUBLIC_`, чтобы переменная отладки `NEXT_PUBLIC_DEBUG` была одной для портала и игры.
- Альтернатива: R3F внутри Next. Отвергнуто: игра живёт во фрейме, а не в страницах Next, и теряется изоляция.
- Альтернатива: библиотека three.js положена в `vendor/` вручную без сборщика, как у `city-builder`. Отвергнуто: игра на тысячи строк TypeScript с тестами требует сборщика и типов.
- Альтернатива: Babylon.js, PlayCanvas. Отвергнуто: тяжелее и не нужны.

### D2. Симуляция отдельно от рендера

```
ввод -> sim.step(dt) -> состояние -+-> render (three.js, чтение)
                                   +-> HUD (DOM, подписка)
```

- `sim/` не импортирует three и DOM. Шаг фиксированный (60 Гц, накопитель времени), время смены - время симуляции, а не часов. Скрытая вкладка ставит игру на паузу.
- HUD - обычный DOM-слой над canvas. Он читает снимок состояния через простое хранилище с подпиской и обновляется не чаще 10 раз в секунду. Библиотеки интерфейса нет.
- Альтернатива: Preact или React во фрейме. Отвергнуто: лишняя зависимость ради десятка элементов.
- Случайность идёт из seeded-генератора (mulberry32). Весь день воспроизводим по seed.
- Общие типы лежат в `src/contracts.ts` и согласуются до начала параллельной работы.

### D3. Уровень как данные

Конфигурация уровня описывает прямоугольники мебели и станций на сетке 0.5, точки столов и стульев, окно выдачи, дверь, слоты очереди, параметры (таймер, меню, число столов, официантов, терпение). Из неё же строятся навигационная сетка и коллизии. Меши мебели расставляются по тем же данным.
- Альтернатива: брать навигацию из загруженных мешей. Отвергнуто: тесты и бот не должны зависеть от glTF.
- Три уровня используют один набор моделей, отличаются раскладкой и параметрами.

### D4. Ввод: один нормализованный интерфейс

Слой ввода собирает клавиатуру (по `event.code`, чтобы русская раскладка не ломала WASD, E и Q), мышь (`pointer`-события, `contextmenu` отключается) и касания (по `pointerId`, `touch-action: none`) в структуру `{ moveVector, actionPressed, workHeld }`. Симуляция не знает об устройстве. При потере фокуса ввод сбрасывается. Режим касаний включается по `(pointer: coarse)` и первому касанию.
- Взгляд хранится как индекс 0..7 и выбирается по `moveVector` с гистерезисом на границах секторов. Плавный поворот рисует рендер, симуляция использует индекс сразу.

### D5. Движение игрока и выбор цели

Игрок - круг, столкновение с прямоугольниками мебели со скольжением вдоль стены. Цель взаимодействия - ближайший объект к точке перед игроком по направлению взгляда (около 0.9 вперёд), с допуском. Цель подсвечивается.
- Альтернатива: физический движок (rapier, cannon). Отвергнуто: геометрия сеточная, лишняя зависимость и вес.

### D6. Предметы и рецепты - данные

Предмет описывается видом и состоянием (`steak/raw`, `patty/cooked`, ...). Станции и рецепты - таблицы переходов (`резка`: состояние A -> B за N секунд удержания; `готовка`: A -> B -> сгоревшее по таймерам). Тарелка - контейнер с мультимножеством ингредиентов. Как только содержимое совпадает с рецептом блюда, тарелка превращается в готовое блюдо (меш `food_*`).
- Сковороды и кастрюли закреплены на плитах и не переносятся.
- Промежуточные слои бургера рисуются стопкой мешей (`bun_bottom`, `burger_cooked`, `*_slice`, `bun_top`) до превращения в готовое блюдо.

### D7. Расписание дня и «бюджет работы»

Весь день (время прихода, размер группы, блюда) строится в начале уровня из seed. Каждое блюдо несёт трудоёмкость, а суммарная нагрузка в скользящем окне ограничена долей (начально 70%) пропускной способности эталонного бота. Приходы ограничены окном от 0 до T-60 секунд.
- Альтернатива: пуассоновский поток без ограничений. Отвергнуто: возможны всплески, которые невозможно обслужить, а при нулевой терпимости это нечестный проигрыш.
- Расписание задаёт знаменатель для HUD («обслужено X из N») и `maxScore`.
- При запуске уровня seed выбирается случайно из списка проверенных (каждый seed заранее прогнан ботом, см. D11). Так разнообразие остаётся, а невыполнимого расписания не бывает.

### D8. Терпение двух фаз

Фаза A (очередь): фиксированное время на уровень. Фаза B (за столом): `базовое + k * трудоёмкость блюда + запас на путь официанта`. У каждого клиента свой таймер, истечение у любого члена группы - провал смены. Остаток терпения при подаче определяет чаевые (`score`). Значения и коэффициенты - в конфиге уровня и калибруются ботом.

### D9. Навигация: A* по сетке

Сетка 0.5, восемь соседей без срезания углов, эвристика octile, затем сглаживание по линии видимости. Препятствия: мебель, раздутая на радиус агента, стулья чужих мест. Агенты NPC сталкиваются только со статикой, между собой и с игроком расталкиваются мягко (силой разделения), а не блокируют друг друга. Если путь не продвигается дольше порога, он перестраивается.
- Альтернативы: навигационный меш (избыточно для сеточной раскладки), RVO/ORCA (избыточно для 2-6 агентов), поле потоков на каждую цель (целей много, A* дешевле).
- Один модуль пути используют официанты и клиенты.

### D10. Назначение заказов официанту

Блюдо в окне привязывается к самому старому открытому заказу того же вида (FIFO по времени появления заказа). Свободный официант с минимальной длиной пути до окна берёт тарелку. Вместимость: 1 тарелка (easy, medium), до 2 на hard, при двух тарелках на один стол они идут одним рейсом.
- Альтернатива: игрок выбирает стол при сдаче. Отвергнуто: усложняет управление и противоречит идее «официант принимает решение».

### D11. Проверка выполнимости эталонным ботом

Бот в vitest проходит уровень в симуляции (жадный планировщик, идеальное движение по A*, без ошибок) и даёт нижнюю оценку времени. Тесты требуют: все клиенты дня обслужены до T, терпение не истекает, очередь не превышает число слотов, последние 60 секунд достаточны для обслуживания очереди. Выполняется для набора seed на каждый из трёх уровней.
- Альтернатива: ручное тестирование. Отвергнуто: не воспроизводимо при изменении параметров.

### D12. Завершение смены через мост

Фазы симуляции: `ready` -> `running` -> `failed` или `finished`.
- Успешный конец (все обслужены, в том числе досрочно) или таймер без обслуженных клиентов: `PortalBridge.finish({ score, maxScore, completed })`.
- Провал (уход клиента): симуляция замирает, игра показывает оверлей с причиной, после кнопки «Продолжить» вызывает `finish` с `completed=false` и набранным `score`.
- Выход игрока из меню паузы: `PortalBridge.exit()`, результат не сохраняется (экран «Уровень не завершен» рисует портал).
- Фатальная ошибка (нет WebGL, не загрузились модели): `PortalBridge.reportError(...)`, портал показывает экран с повтором.
- После отправки результата или выхода игра останавливает цикл и не отправляет ничего повторно.

### D13. Готовность и загрузка

Сначала загружаются все нужные модели, затем вызывается `PortalBridge.onStart`: первый вызов сообщает порталу о готовности. Пока идёт загрузка, портал показывает собственный индикатор. `runtime.readyTimeoutSec` - 60 секунд (по умолчанию 30 мало для около 50 моделей на медленном канале). Уровень берётся из сообщения старта, а не из адреса. `durationSec` считает портал от старта, поэтому стартовый экран с подсказками входит в него: он короткий и без времени ожидания.

### D14. Ассеты и персонажи

Нужные модели (около 50) и атлас копируются в `web/game-src/cooking/public/models/`, Vite кладёт их в `public/game-builds/cooking/models/`. Все пути относительные, `GLTFLoader` и текстуры грузятся из той же папки: изолированный фрейм разрешён благодаря CORS-заголовку портала. Персонажи (повар, официант, клиенты) строятся из примитивов в цветах атласа, покачивание при ходьбе по синусу. Иконки блюд для HUD рендерятся один раз из glTF во внеэкранный canvas, запасной вариант - текстовая подпись.
- Альтернатива: сторонний пак персонажей с анимациями. Отложено: не меняет контракты, лицензию надо проверить отдельно.
- Альтернатива: FBX или OBJ. Отвергнуто: glTF стандарт веба, нужен один формат.

### D15. Камера и раскладка

Камера без поворота, наклон около 50°, перспектива, весь ресторан в кадре. Передняя стена заменена на `wall_half`. Кухня и зал разделены стеной с окном выдачи, дверь с улицей и слоты очереди находятся в зоне видимости камеры. Оси камеры совпадают с осями сетки: W всегда означает «вверх» на экране. Размер canvas следует за размером фрейма (на телефоне и на ПК он разный).

### D16. Отладка и мост-копия

`NEXT_PUBLIC_DEBUG=true` включает отладочный оверлей (сетка навигации, пути, зоны). Значение подставляется при сборке (`dev:cooking` читает его на лету). Копия `portal-bridge.js` берётся из `sdk/web/` шагом перед сборкой, а её путь добавляется в `bridgeCopies` теста `sdk/sdk-consistency.test.ts`, чтобы копия не отставала.

## Начальные значения баланса

Значения лежат в конфиге и калибруются ботом, на спецификации они не влияют.

| Операция | Значение |
|---|---|
| Резка (удержание) | 2 с |
| Котлета на сковороде | готова за 6 с, сгорает ещё через 6 с |
| Окорок в духовке | готов за 8 с, сгорает через 8 с |
| Рагу в кастрюле | готово за 10 с, сгорает через 10 с |
| Время еды клиентом | 12 с |
| Бюджет работы | 70% пропускной способности бота |

## Risks / Trade-offs

- **[Загрузка glTF, `.bin` и текстур из изолированного фрейма]** -> первая задача проверяет это в портале в обычном браузере, пути относительные, при проблемах - упаковка моделей в один файл.
- **[Встроенная панель браузера блокирует iframe]** -> ручная проверка сборки по прямому адресу, потока портала - в обычном Chrome.
- **[`durationSec` считает портал, он включает стартовый экран и паузу]** -> принято, стартовый экран короткий. Время смены внутри игры считается по времени симуляции.
- **[Нулевая терпимость делает игру суровой]** -> щедрое терпение на easy, расписание с бюджетом работы, проверка бота.
- **[NPC застревают и проигрыш не по вине игрока]** -> мягкое расталкивание, перепланирование пути, тест на отсутствие дедлоков в симуляции.
- **[Производительность на слабых телефонах]** -> ограничение pixel ratio, один атлас, статичный декор через инстансинг, без тяжёлых теней.
- **[Нет персонажей в паке]** -> примитивы в стиле пака, смена на другой пак не затрагивает логику.
- **[Лицензия пака]** -> подтвердить перед публикацией, файл лицензии положить рядом с ассетами.
- **[Ввод: ПКМ, стрелки, потеря фокуса]** -> `contextmenu` и скролл блокируются внутри фрейма, сброс ввода на `blur`.
- **[Сборка и модели лежат в git]** -> как у `city-builder`; размер модели ограничен выбором около 50 файлов. Коммитит пользователь.
- **[Общие файлы проекта]** -> правки `scripts/check-dashes.mjs` (папка `game-src`), `sdk/sdk-consistency.test.ts`, `package.json` минимальны и отмечены в задачах.

## Migration Plan

Новая игра, миграций нет. Деплой - статическая сборка Next.js плюс собранная игра в `public/game-builds/cooking/`. Откат: убрать строку из реестра, остальной код игры не влияет на портал. Данные LocalStorage используют существующую схему результатов (их пишет портал).
